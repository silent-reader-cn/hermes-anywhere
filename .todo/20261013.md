### #195 聊天媒体/附件链接的 emoji 前缀换成矢量图标（下载文件名同步去装饰字符）[已收口]

- **位置**：`lib/features/chat/widgets/chat_media_parser.dart`（生成链接文案）、
  `lib/features/chat/widgets/markdown_styles.dart`（新增 `MediaLinkIconBuilder`）、
  `lib/features/chat/widgets/media_kind_icons.dart`（类型图标唯一出口）、
  `lib/features/chat/widgets/user_attachment_block.dart`（改读同一份映射）、
  `lib/features/downloads/download_save_service.dart`（文件名兜底剥离装饰符号）、
  `third_party/flutter_markdown/lib/src/builder.dart`（vendored 补丁第 5 节）。
- **现象（主人报）**：聊天里 agent 发来的附件/音频/视频链接前面恒有一个 emoji
  （📎 / 🎵 / 🎬），**下载时文件名也带**（落到 `Downloads/📎 spec.pdf`）。
- **根因**：类型前缀被写进了「正文文案」——`ChatMediaParser` 把 `MEDIA:` 引用转成
  `[📎 name](url)` 形式的 Markdown；链接文案又是 `onTapLink` 的 `linkText`，被
  附件预览页当标题、被下载按钮当 `filename`，而 `sanitizeFileName` 只过滤路径
  分隔符与文件系统非法字符，emoji 不在名单里 ⇒ 装饰字符一路进了磁盘文件名。
  另外 emoji 字形在 Windows / Android / iOS 三端各不相同，观感与一致性都差。
- **现状 vs 预期**：现状 = 文案带 emoji、文件名带 emoji、三端字形不一致；
  预期 = 矢量细线图标表达类型，链接文案恒等于真实文件名。
- **做法**：解析器输出改为 `[真实文件名](url "hermes-media")`（标记写在 `title`，
  不污染文案）；`MediaLinkIconBuilder` 只给带标记的链接**前置** 13px Cupertino
  图标（音频 `music_note` / 视频 `film` / 文档 `doc_text` / 其它 `paperclip`，
  与用户气泡附件条同一份映射），普通网页链接不带标记 → 默认渲染与点击行为不变。
  为让「前置」可行，vendored `flutter_markdown` 的 `a` 构建器语义由「替换链接文字」
  改为「前置一个 inline span」，并补上该分支漏掉的 `_linkHandlers.removeLast()`
  （原实现会把链接识别器留在栈上、误挂到后续正文与图片）；既有 `sanitizeFileName`
  再兜底剥离装饰性符号/emoji，防止别的调用点再漏。
- **验收（实测）**：`analyze` 零告警；受影响测试 80 条全绿（含新增
  `test/features/chat/media_link_icon_test.dart` 4 条：图标按类型渲染 / 普通链接
  不加图标 / 链接仍可点且 linkText 为纯文件名 / **链接之后的普通文字不带识别器**，
  以及 `download_save_service_test` 的 emoji 剥离用例）；全量 `flutter test` 全绿；
  明暗双态真渲染截图目检（图标随链接色、无 emoji、无溢出裁切）。
- **备注**：WebUI（浏览器端，`D:\hermes-webui`）同款 emoji 前缀另行替换为仓内
  内联 SVG 图标（独立提交）；App 内置的 WebUI sidecar 需重新出包才会带上那一项。
- **待办（未做）**：主人当前跑的是已编译客户端 ⇒ 需重新出包（Windows
  `flutter-windows-release` / Android `flutter-android-release`）才能看到效果。

### #196 会话内永久卡「生成中 · 已工作 MM:SS」（服务端早已收尾）[已收口]

- **位置**：`lib/features/chat/chat_controller.dart`（`_completeCurrentResponse` / `_appendAssistantToken` /
  新增 `_recoverOrphanedDisplayIfNeeded` 与 `_isSettledForContentFrames`）、
  `lib/features/chat/chat_providers.dart`（看门狗新增两个配置项）。
- **现象（主人报）**：某台远程 Windows 客户端在会话内一直显示「生成中 ≈24 tps · 已工作 317:40」、
  300+ 分钟不吐新内容；侧边栏该会话没有生成中图标；其他端连同一服务（`oa.heshenghe.cn:50001`）
  看该会话早已完成。只有杀 App 才好。
- **服务端侧已排除**：会话 `active_stream_id` 已清、`pending_*` 为空、383 条消息完整，当日 10 篇
  run journal 全以 `stream_end / terminal_state=completed` 收尾，`/health?deep=1` 里没有该流
  ⇒ 纯客户端显示态僵尸（侧边栏读服务端 `active_stream_id`，故正常）。
- **根因（HEAD 下逐条实证）**：① done 路径的收尾出口 `_applyDone` 只调 `_completeCurrentResponse`、
  **全程不调** `_finishStream`，而清 `turnStartedMillis` 全仓只有 `_finishStream` ⇒ 「已工作」计时
  永不归零（RED 实证：回退该行后 `turnStartedMillis` 仍非空）；② 收尾后到达的迟到/重放内容帧经
  `_appendAssistantToken` → `_appendToStreamingMessage` → `_ensureStreamingAssistantMessage` 会
  **重建**流式子气泡（临时探针实证：phase=idle / hasCompletedResponse=true 时仍新建 `stream-*` 行）；
  ③ 该组合下**所有**自愈链都被闸门挡在外面（transport-stale 要 activeStreamId、死区兜底要进行中
  相位、G5 要 streaming+streamId、stall guard 要刚有用户动作）⇒ 无路径可清。
- **做法**：F2 `_completeCurrentResponse` 补 `clearTurnStartedMillis` + `_discardPendingStreamBuffers()`
  （取消 merge/reveal 定时器、丢弃待落账缓冲，对称加固）；F1 1s 看门狗新增
  `_recoverOrphanedDisplayIfNeeded`（无活跃流 + 相位已离场 + 子气泡/计时残留 → 清显示残渣 +
  退本地流式临时行 + 兜底拉一次权威 transcript，带冷却）；F1b `_appendAssistantToken` 加
  `_isSettledForContentFrames` owner-alive 早退（收尾后的内容帧不再进显示态）；新增配置
  `orphanDisplayStallThreshold`（20s）/ `orphanDisplayCooldown`（30s）。
- **验收（实测）**：`analyze` 零告警；新增 `test/features/chat/chat_orphan_display_recovery_test.dart`
  7 例（含 4 条反向：stream_end 路径不留残渣 / 收尾后迟到帧不得重建气泡 / 真回合不得被清 /
  有活跃流的强制刷新走状态链）；**RED 校验**：回退 ① ⇒ 用例 1 精确红、回退 F1 ⇒ 用例 4 红，
  其余用例保持绿（零误伤），恢复后 sha256 与修复版一致；全量 `flutter test` **5892 通过 /
  230 skipped / 0 失败**；金照基线 `test/golden/golden_screens_test.dart` 单跑 22 通过。
  提交 `3c42637`。
- **备注**：主人当前跑的是已编译客户端 ⇒ 需重新出包（Windows `flutter-windows-release` /
  Android `flutter-android-release`）才生效；远端那台的导出日志仍可用来进一步确认重建子气泡的
  那一步是怎么被触发的。

### #197 会话菜单新增「强制刷新」（显示态死锁的用户级出口）[已收口]

- **位置**：`lib/features/chat/chat_controller.dart`（新增 `forceRefresh()`）、
  `lib/features/chat/chat_page.dart`（五族会话菜单）、`lib/l10n/app_localizations.dart`。
- **需求（主人 2026-10-13）**：在会话的菜单里提供「强制刷新」选项 —— 卡在生成中时不用再杀 App。
- **做法**：`forceRefresh()` 有活跃流 → 走既有状态链（status 探活 → 重拉续传 / 重放 / 按 transcript
  收尾），**不硬清显示态**（不打断真回合）；无活跃流 → 清显示残渣 + 丢弃待落账缓冲 + 拆恢复闩锁
  （预算/退避/冷却）+ 拉权威 transcript 并退掉本地流式临时行。纯读操作，返回是否执行到位。
  菜单项 key `chat-action-force-refresh`（族①「会话」，紧随「归档」），刻意放在 `isReadOnly` 闸门
  之外（纯读操作，只读会话同样卡得住）；文案 `forceRefresh` / `forceRefreshDone` /
  `forceRefreshFailed`（l10n 双语），结果经 `setNotice` 给轻提示。
- **验收（实测）**：`analyze` 零告警；菜单规格表同步新项（`chat_actions_menu_icons_test` 只读态
  分组收敛用例继续绿）；新用例 6/7（孤儿态刷新 → 清残渣 + 拉 transcript；有活跃流 → status 探活
  1 次且不清流）；相关 47 例全绿；全量 5892 通过 / 0 失败。提交 `3c42637`。
- **备注**：同 #196 需重新出包才可见。

### #198 中文名附件 404：markdown 链接目标被二次编码（附路径形态规整）[已收口]

- **现象（主人报）**：Boss Agent 会话里我发的 Excel/Word 打开就 404。App 诊断日志实证：
  `GET /api/media?path=D%3A%2Fprojects%2Fsloth%2Fdocs%2F%25E6%25A0%2591%25E6%2587%2592…xlsx` →
  `404 {"error":"not found"}`（`%25E6` = `%E6` 又被编一次；请求无 `session_id`；走 frp 公网口 50001）。
- **根因（客户端）**：`package:markdown` 会把链接目标里的非 ASCII 规范化成百分号转义 ⇒ `onTapLink`
  拿到的 href 已是 `D:/…/docs/%E6%A0%91…xlsx`；`ChatMediaResolver.resolveMediaUrl` 随后又
  `Uri.encodeComponent` 一次 ⇒ `%E6`→`%25E6`。服务端解一次码后去找**字面量** `%E6%A0%91…xlsx`
  的文件 ⇒ 404。**纯 ASCII 名不受影响** —— 所以现象是「只有那几份中文名文件打不开」；
  服务端本身没问题（同路径单次编码实测 200）。
- **位置**：`lib/features/chat/widgets/chat_media_parser.dart`（`resolveMediaUrl` + 新增
  `_decodeLinkDestination` / `_normalizeDriveForm`）。
- **做法**：① 入口先安全解码链接目标（含 `%` 才解、失败原样返回不抛、http/data 原样透传），
  保证「原始中文路径」与「已编码链接目标」结果一致（幂等）；② 盘符形态规整：`file:///d/…`
  （Windows `toFilePath()` 会变成 `\d\…`）与裸 MSYS 形 `/d/…` ⇒ 统一 `D:/…`（不规整会被服务端
  按 cwd 解析 ⇒ 403，即上次说的 403 那一类）；③ **含分隔符但非绝对**的路径（`docs/x.xlsx`）改走
  `/api/file/raw`（`/api/media` 只认绝对路径），前导 `/`（POSIX 形 `/tmp/x.png`）仍算绝对，既有路由不回归。
- **验收（实测）**：`analyze` 零告警；新增 `test/features/chat/media_link_encoding_test.dart` 8 例 +
  整链 widget 例（markdown 渲染 → onTapLink → 解析，与真实日志 URL 逐字符对照）；相关 68 条全绿；
  **端到端**：修复后两种形态 URL 在本机 30002 与 frp 公网 `221.176.152.14:50001` 均 200（21232 字节），
  日志里那条二次编码 URL 复现 404。
- **备注**：WebUI 前端同款处理是先 `decodeURIComponent` 再 encode（`_markdownHref`）⇒ 无此缺陷，
  本次只改 App。另：WebUI 工作区预览 Office 的 503（缺 python-docx/openpyxl/python-pptx）已用 uv
  装进运行中的 venv 修好（惰性 import，免重启）。
- **待办（未做）**：主人当前跑的是已编译客户端 ⇒ 需重新出包（Windows/Android）才能生效。
